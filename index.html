Data leakage, explained · from a CSE445 study at North South University

The column that fooled every model

We trained classical models, tabular foundation models, fine-tuned transformers and an LLM to predict which bank customers would say yes to an offer. One column made all of them look better than they were. Here is how it happens, and how to catch it.

The task

A Portuguese bank phoned customers to sell a term deposit. The data, published on the UCI repository, records each call: who the customer is, when they were called, how long the call lasted, and whether they said yes. Only about 11% did.

The job of a model is to help the bank decide whom to call next. So the prediction has to be made before the phone rings.

When do you know each value?

Every column in a dataset was recorded at some moment. The question that matters: was it recorded before the moment you need the prediction?

In the real data, training on 2008–2009 and testing on 2010 dropped ROC-AUC to 0.6461. And 2010 was a different world: about 52% said yes, against about 11% overall. In a period like that, a model that always answers "yes" already reaches an F1 of 0.68. Raw F1 from different periods cannot be compared; compare each model against a simple baseline on the same period.

Catching it

  1. Would I know this value when I make the prediction? Ask it for every column, especially anything with duration, status, final or result in its name.
  2. Does one column carry the whole model? Remove it and retrain. A big drop deserves an explanation.
  3. Does the score survive a time-based split? Train on the past, test on the future.
  4. Are the same rows in both train and test? Duplicates make the test set partly a memory test.

I turned these checks into a small Python library, LeakGuard:

pip install git+https://github.com/Israt24hub/leakguard
leakguard bank.csv --target y --time-col contact_date
